#
# Built from npc/quests/quests_rachel.txt (rAthena, L0ne_W0lf, v3.6) — NOT
# from the wiki alone, since the wiki had wrong coordinates/mechanics in
# several places (see EVENTMACRO.md "Real example"/comparison notes).
#
# Server confirmed: Pre-Renewal. Lost Child Quest: not yet done on this char.
#
# IMPORTANT CAVEATS (per EVENTMACRO.md Debugging conventions):
# 1. RQ_00_Setup turns on `do conf autoTalkCont 1` once, globally, for the
#    whole session — this makes OpenKore auto-press "continue" on every
#    plain dialogue screen by itself (see src/Task/TalkNPC.pm), so every
#    `do talknpc` sequence below carries ONLY the `rN` (menu choice) tokens,
#    no `c` tokens at all. This was cross-checked against the live
#    rathena/rathena script to get the select() positions/indexes right.
#    autoTalkCont only affects `do talknpc`-driven conversations (real
#    clickable NPCs) — the few OnTouch-triggered dialogues (walking onto an
#    invisible trigger tile: window, maze checkpoints, bloody spot, gate,
#    key, door, eavesdrop) are NOT started via `do talknpc`, so those still
#    use explicit `do talk cont`/`do talk resp N` sequences; whether
#    autoTalkCont also auto-continues those is unverified — if they turn
#    out to double-continue/error, that's the thing to check first.
#    If a step stalls: `do conf debugDomains eventMacro`, then
#    `eventMacro auto <name>` to see what's actually blocking.
# 2. $rachel_donate (server-wide donation counter) must already be >= 10000
#    for any of the ra_tem_q content below to be reachable at all — this
#    file assumes that's already true on FoxRO. If Nemma still shows the
#    donation UI instead of "the gate won't open", the counter isn't there
#    yet and this whole chain is unreachable until it is.
# 3. The candy-kid step includes a genuine 50% server-side RNG gate
#    (rand(1,2) in the script) — this is NOT run-once, so a failed attempt
#    just retries on the next timeout. It also branches further on whether
#    you're already carrying a "Candy" item (529) — RQ_03/RQ_04 farm it
#    automatically (rule 6/9) before the walk-and-talk chain even starts.
#    Candy is NOT sold by any NPC (checked divine-pride.net) — only dropped
#    (~1.6-1.75%) by Marin/Cookie/Myst Case at xmas_dun01 (Toy Factory
#    Warehouse). Low drop rate for a 1-item requirement, but automated
#    per the user's call rather than left as a manual step.
# 4. Pope's two free-response prompts use `do talk text "..."` rather than
#    being crammed into a talknpc sequence, since raw text input mid-dialogue
#    doesn't fit the c/rN grammar.
# 5. RQ_00_Setup triggers on `InMapRegex` (not `OnCharLogIn`) — it fires once
#    you're on any map OTHER than the quest's own map cluster (rachel,
#    ra_temple, ra_temin, ra_temsky, ra_in01, ra_fild01, que_rachel,
#    que_san04, ra_san01, ice_dun01, xmas_dun01, hugel). Since it's
#    `run-once 1`, if the character happens to already be standing on one of
#    those maps when this file loads, setup won't fire until you leave that
#    cluster once — walk out and back in if that happens.
#
# --- SETUP: do this by hand before using this file ---
#
# 1. Add this to your control/config.txt (or profile config.txt) — getAuto
#    is config.txt-only, there is no console command for it:
#
#    getAuto Glacial Heart {
#        minAmount 0
#        maxAmount 40
#        batchSize 0
#        passive 0
#        disabled 0
#    }
#    getAuto Candy {
#        minAmount 0
#        maxAmount 1
#        batchSize 0
#        passive 0
#        disabled 0
#    }
#
# 2. !include this file from your main eventMacros.txt. Path is relative to
#    wherever the !include line itself lives — e.g. from
#    account/<profile>/eventMacros.txt (two levels below repo root):
#
#    !include ../../RachelQuests.txt
#
#    (add one more ../ per extra folder level, e.g. account/hunting/<profile>/)

##############################################################################
# SECTION 0.55 — Reload/restart recovery. eventMacro wipes every custom $var
# and every `run-once` counter on `reload eventMacro` / plugin reload (see
# eventMacro.pl: "this must be a file reload... Unloading all current
# config."). RQ_00_Setup above only re-initializes vars while crossing OUT of
# the quest map cluster (InMapRegex, negated) — so a reload while already
# standing on rachel/ra_in01/ra_temin/etc leaves every $var *undefined*
# instead of 0/whatever it was, and undefined never matches any `VarValue
# $var N` check. Net effect: every var-gated automacro below just stops
# matching ("macros ignored"), and the one gate that used QuestInactive as a
# stand-in for "not started yet" (LC_01) could fire backwards once run-once
# reset too (fixed above with QuestAllListInactive).
#
# These automacros re-derive what they can from LIVE, reload-proof signals —
# real server quest state, or current map/position — instead of trusting
# anything eventMacro itself remembered. Each is `run-once 1`, so it settles
# state once per session then gets out of the way.
#
# KNOWN GAP: the que_rachel maze (RS_04-RS_11) has no quest ID at all until
# the gate is pushed, and neither does the Panno/Firecracker-delivery leg
# (RS_12-RS_16) or the guard/door/Pope/eavesdrop/key leg (RS_19-RS_27) before
# quest 8104 appears — the server gives no signal to tell exactly which
# sub-step of those you were on. RQ_00R3_RecoverMazeReentry below re-walks
# the maze from its own entrance if you reload mid-maze (not exact, but not
# from zero either — Track A/B materials, acceptance, and everything with a
# real quest ID all resume correctly). A reload landing exactly inside the
# Panno/guard/Pope/eavesdrop legs still resumes imprecisely (may redo one
# already-finished NPC line) since those legs are physically un-addressable
# without guessing coordinate windows on a heavily-reused map (ra_temin) —
# ask if precise per-zone recovery for those legs is wanted, since guessing
# it wrong risks skipping a real step instead of just repeating one.
##############################################################################

automacro RQ_00R1_RecoverSetup {
	InMapRegex /^(rachel|ra_temple|ra_temin|ra_temsky|ra_in01|ra_fild01|que_rachel|que_san04|ra_san01|ice_dun01|xmas_dun01|hugel)$/
	run-once 1
	exclusive 1
	priority 20
	call {
		log "RQ_00R1_RecoverSetup: re-applying idempotent config once this session, in case RQ_00_Setup's map-gated trigger didn't fire since the char was already inside the quest map cluster on load/reload"
		do conf autoTalkCont 1
		do iconf Glacial Heart 40 0 0
		do iconf Firecracker 20 0 0
		do mconf Siroma 2 0 0
		do iconf Candy 1 0 0
		do mconf Marin 2 0 0
		do mconf Cookie 2 0 0
		do mconf Myst Case 2 0 0
		$setupDone = 1
	}
}

# BUGFIX: this used to also default every progress var to 0 right here,
# relying on `priority 20` to run before RQ_00R2-R5 (priority 0) in the same
# startup pass so the more specific recoveries would override these
# defaults. Confirmed live that assumption is wrong: RQ_00R1 (InMapRegex,
# hooked to packet_mapChange/in_game) and RQ_00R3 (InMap, its own separate
# hook) don't reliably get dispatched in the same check cycle just because
# they're both true after a reload - `priority` only orders automacros
# competing within ONE dispatch pass, not across genuinely separate hook
# firings. RQ_00R3 fired first and correctly recovered $rsGateStage=3, then
# RQ_00R1 fired afterward and stomped it straight back to 0. Fixed by making
# the baseline-zero case mutually exclusive by its own conditions instead of
# by hoping for ordering: this only fires when NONE of RQ_00R2/R3/R4/R5's
# own trigger conditions are true, so there's nothing for it to clobber.
automacro RQ_00R1b_RecoverBaseline {

	NotInMap que_rachel
	NotInMap que_san04
	QuestAllListInactive 8092,8100,8104
	run-once 1
	exclusive 1
	call {
		log "RQ_00R1b_RecoverBaseline: no more specific recovery signal applies, defaulting every progress var to 0/not-done as a baseline"
		$trackA_done = 0
		$trackB_done = 0
		$rsGateStage = 0
		$inMaze = 0
		$rsPopeStage = 0
		$rsEavesdropStage = 0
		$rsPastOut1 = 0
		$rsKeyStage = 0
		$rsHolyGround = 0
		$lcMerchant1Done = 0
	}
}

# SECTION 0.5 — Firecracker purchase, moved to the very start (per user
# request) so it runs alongside the other loot prerequisites instead of
# waiting for rsGateStage 14 later in the Sanctuary chain. Gated on
# `ConfigKeyNot raTrackADone 1` (see RQ_01_Restock below for the same
# pattern) - once Track A delivers the Firecrackers, none are needed again
# for the rest of the chain, so stop buying/farming even if the inventory
# count later drops below threshold for an unrelated reason.
#
# BUGFIX: this was `VarValue $trackA_done 0` originally. $trackA_done is an
# eventMacro var, wiped on every reload, and the narrow window between "Track
# A actually finished" and "a specific quest-ID/map recovery signal exists
# for it" (see SECTION 0.55's own documented gap) kept letting a reload
# reset it back to 0 - sending the character all the way back to Hugel to
# re-buy Firecrackers it already delivered, confirmed live more than once.
# `raTrackADone` is a plain control/config.txt key instead (set by
# RS_16_GiveFirecrackers alongside $trackA_done) - config.txt is a real file
# that survives every reload, so this gate can't desync no matter which gap
# a reload happens to land in.
##############################################################################

automacro RQ_00B_BuyFirecrackers {
	VarValue $setupDone 1
	ConfigKeyNot raTrackADone 1
	InInventory "Firecracker" < 20

		log "RQ_00B_BuyFirecrackers: going to hu_in01, Party Supplies Shop, to buy Firecrackers"
		do c RQ_00B: heading to the Party Supplies Shop in Hugel to buy Firecrackers.
		do conf lockMap hu_in01
		do conf lockMap_x 23
		do conf lockMap_y 311
		do conf lockMap_randX 1
		do conf lockMap_randY 1
	}
}

# so r0 = Buy). Confirmed via `npc list` that its real in-game name has NO
# "#hu_in01" map-disambiguation suffix, unlike Nemma/Vincent/etc elsewhere in
# this file - it's just "Party Supplies Shop", plain. Not run-once, since one

	VarValue $setupDone 1

##############################################################################
# SECTION 0.6 — Autoloot: any time an item drops on the ground, send the
# server's @autoloot chat command (same command farmermacro.txt already uses
# via `do c @autoloot`). Not tied to a Rachel quest step — general utility,
# active for the whole session. Reacts to the item_appeared hook
# (Network/Receive.pm), fired once per dropped item; the 2s timeout throttles
# repeat firing when several items drop in the same tick (e.g. AoE kill).
#
# BUGFIX: eventMacro's substitue_variables() (Runner.pm) scans every command
# string — not just condition text — for bare $/@/% variables and replaces
# them; an unescaped "@autoloot" gets read as the array variable @autoloot
# and replaced with that array's SIZE (0, since it's never declared), which
# is why the bot said "0" instead of "@autoloot". Escaping as "\@autoloot"
# stops the substitution (backslash-escaped vars are skipped, then the
# backslash itself is stripped before the command runs).
##############################################################################

automacro RQ_00C_AutolootOnDrop {
	SimpleHookEvent item_appeared
	VarValue $setupDone 1
	timeout 2
	call {
		log "RQ_00C_AutolootOnDrop: item appeared on the ground, sending \@autoloot"
		do c \@autoloot
	}
}


##############################################################################
# SECTION 0.8 — Rachel Kafra save point + zone config. Condition is a plain
# location regex (InMapRegex, same style as RQ_00_Setup's negated version of
# this exact pattern — see caveat #5 above) rather than an OnCharLogIn event:
# fires the first time (run-once) the character is on rachel or any ra_fild*
# map, regardless of whether that's from a fresh restart or just normal
# quest-chain routing passing through. `priority 10` + `overrideAI 1` make
# sure this wins the race against the farm automacros below, which have no
# map gate and can otherwise grab exclusivity first and drag the character
# off to ice_dun01/xmas_dun01 before this ever gets a chance to run.
#
# NOTE: earlier version used `override-Ai 1`, which is NOT a real eventMacro
# parameter (the real one is `overrideAI`, camelCase, no hyphen — see
# EVENTMACRO.md's parameter table). An unrecognized parameter key gets
# parsed as a *condition* instead; eventMacro then fails to find a matching
# Condition::override-Ai module and silently drops the whole automacro with
# just a console warning. That's why this block never fired.
#
# BUGFIX: `run-once` alone isn't reload-safe — it resets on every
# `reload eventMacro`, and InMapRegex rachel/ra_fild* is true for most of
# this quest chain's runtime, so without another gate this automacro was
# re-firing on *every* reload, seizing overrideAI+exclusive+priority 10 and
# dragging the character back to the Kafra save point mid-quest — and if a
# second reload landed while that was running, it could leave the character
# stuck partway. `ConfigKeyNot saveMap rachel` checks control/config.txt
# directly (a real file, untouched by eventMacro reloads) instead of
# eventMacro's own volatile run-once state, so this now only fires once,
# ever, until saveMap actually changes away from rachel.
##############################################################################

automacro RQ_00E_GoRachelKafra {
	InMapRegex /^(ra_fild\d+|rachel)$/
	ConfigKeyNot saveMap rachel
	exclusive 1
	overrideAI 1
	priority 10
	run-once 1
	call {
		do c "RQ_00E_GoRachelKafra: heading to the Rachel Kafra to save"
		do ai manual
		do move rachel 117 137
		do talknpc 109 138 c r~/Save/ n
		do conf storageAuto_npc rachel 109 138
		do conf sellAuto_npc ra_in01 257 269
		do conf BuyAwak.npc ra_in01 257 269
		do conf BuyButterflyWing.npc ra_in01 257 269
		do conf autoMoveOnDeath 0
		do iconf 13004 0 0 1
		do iconf 1208 0 0 1
		do iconf 1408 0 0 1
		do p saved in rachel
		do conf saveMap rachel
		do ai on
	}
}

# BUGFIX: the real rAthena script (rachel,243,37 "Kid#Candy Addict") has a
# genuine 50% rand(1,2) gate AFTER the "Yeah."/"Sure, I love the stuff~"
# choice — only the lucky roll shows a second menu ("Sure.:No.", with "Sure."
# at index 0) that actually sets ra_tem_q,2 server-side; the unlucky roll
# just closes the dialogue with no further menu and no state change. Blindly
# sending a second response ("r0") after every attempt, or advancing
# $rsGateStage unconditionally, both desync the client from the real server
# quest state (touching que_rachel's maze triggers later no-ops silently if
# ra_tem_q is behind what $rsGateStage thinks it is). So: send only the first
# choice here, then gate the second response — and the stage advance — on
# actually seeing the kid's line that only appears on the lucky roll.
#
# BUGFIX: this used to be `exclusive 1`. eventMacro tracks a single global
# "automacro checking status", and starting a non-interruptible (exclusive)
# macro flips it to PAUSED_BY_EXCLUSIVE_MACRO for as long as that macro's
# Runner is active (Runner.pm:209) — `do talknpc` keeps the Runner active for
# the whole conversation, not just the dispatch. While paused, EVENT-type
# conditions (like RS_02c's `NpcMsg`) are never allowed to fire at all
# (Core.pm:1469 explicitly requires CHECKING_AUTOMACROS/CHECKING_FORCED_BY_USER)
# - and since NpcMsg is a one-shot event, not a polled state, a message that
# streams by while paused is gone for good, never re-evaluated once the pause
# lifts. The kid's "really cool" line arrives strictly *during* this
# automacro's own `do talknpc` conversation, so `exclusive 1` here was
# structurally deadlocking RS_02c against the exact message it needs to see
# - confirmed live: the RNG-lucky-roll response menu was left sitting
# unanswered ("Type 'talk resp #' to choose a response") forever. Dropping
# `exclusive 1` (safe: `running_status` already stops this automacro
# retriggering itself while its own conversation is still active, with or
# without `exclusive`) lets RS_02c react in real time.
#
# BUGFIX: this used to send `r1` as part of the sequence, assuming the
# "do you like candy?" menu always appears. On a repeat visit (already talked
# to him before) the kid has a completely different, shorter brush-off line
# ("Why don't you peep through the windows... Gosh! Some people!") that
# closes the dialogue with NO menu at all - confirmed live:
# "There are still steps to be done but the conversation has already ended
# (current step: r1)". Sequences are rigid (no "answer this IF it shows up"
# branching), so instead of guessing which variant will play, send an empty
# sequence (autoTalkCont handles every plain continue by itself) and let
# RS_02a_CandyKidMenu answer the real "do you like candy?" menu reactively,
# the same event-driven way RS_02c/RS_02d already handle the lines after it -
# if the brush-off variant plays instead, no menu ever appears and nothing
# needs to answer, so the dialogue just closes cleanly.
#
# BUGFIX: `timeout` dropped from 900 to 5. The kid apparently has more than
# two dialogue variants (RS_02d/RS_02e chase two of them by exact phrase, and
# a third, uncaught one showed up live) - rather than keep whack-a-moling
# every possible brush-off line, a short timeout means this automacro itself
# retries any outcome none of the NpcMsg catches recognized, a few seconds
# later. Safe at 5s: `running_status` still blocks it from firing while a
# conversation it started is genuinely still open.
automacro RS_02_CandyKid {
	NpcNear /^Kid#Candy Addict$/
	VarValue $rsGateStage 1
	timeout 5
	call {
		$nx = &arg("$.NpcNearLastPos", 1)
		$ny = &arg("$.NpcNearLastPos", 2)
		log "RS_02: candy kid, RNG-gated, will retry on failure"
		do c RS_02: talking to the Candy Kid about the secret window - has a 50% RNG gate, may need retries.
		do talknpc $nx $ny
	}
}
